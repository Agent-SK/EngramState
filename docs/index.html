01 · MOTIVATION

The tool never changed.
Why read it again?

Function-calling prompts contain mostly static information: tool names, descriptions, arguments, value formats, and examples. Conventional pipelines repeatedly prefill that same text for every request. EngramState treats this information as reusable memory instead of repeated input.

PROMPT BASELINE · EVERY REQUEST

The model rereads the tool specification.

Even a tiny user request is concatenated with static tool knowledge before generation can begin.

“Set a timer for 20 minutes.”
name: set_timer
description: Start a countdown timer on the device.
arguments:
  minutes: integer, required
  seconds: integer, optional
constraints:
  - preserve requested duration
  - reject negative values
  - normalize minutes / seconds
examples:
  "5 minutes"  → set_timer(minutes=5)
  "90 seconds" → set_timer(minutes=1, seconds=30)

+ set_alarm specification
+ create_event specification
+ ... other tool specifications ...

03

Load, then generate

Restore the selected state and start generation from the short live query rather than the full specification.

02 · METHOD

Base knowledge.
Corrective memory.

Each tool is represented by a Base State containing its canonical specification and a Corrective State capturing failure rules and hard cases. The corrective path is activated only when necessary.

05 · PRACTICAL DEPLOYMENT

Designed for constrained devices.

4-bit state storage

Channel-wise state quantization reduces persistent state footprint without requiring full model quantization to change.

Selective loading

Only retrieved tool states enter the execution path, avoiding a runtime context that grows with the entire tool catalog.

Incremental updates

When an existing tool specification changes, its states can be recompiled independently. New tools can be added without rebuilding every stored state.

Stateful backbones

The core formulation targets recurrent/state-space models such as RWKV and Mamba, where reusable model state is a natural deployment primitive.
