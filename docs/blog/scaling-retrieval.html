Technical note 04 · Scaling

Scaling EngramState to larger tool repositories

The important question is not whether 24 tools work. It is which costs grow with the repository, which stay constant, and where retrieval quality begins to matter.

Execution cost stays local to the candidate

EngramState never loads the full state repository for one request. The retriever selects Top-K candidates and the executor loads one candidate state per attempt. This means the cost of a single state-loading + generation step does not increase just because the catalog contains more tools.

What does scale with tool count?

Similarity comparisons increase with the catalog size, just as they do in retrieve-then-prompt systems. In our 100-tool measurement, similarity computation plus Top-K scanning took only 0.0304 ms out of 24.1 ms total retrieval time—about 0.1% of retrieval latency.

Why Hit@4 matters

EngramState can traverse multiple candidates, so Hit@4 is often more operationally meaningful than Hit@1. At 206 tools, the MLP retriever still places the correct tool in the Top-4 about 95.63% of the time.

End-to-end retrieval, not just ranking

A retriever can have good Hit@K and still create a poor system if it is large, slow, or increases retries. We therefore measured the complete pipeline.

Systems lesson: the best retriever for an on-device agent is not necessarily the largest semantic encoder. The retriever itself becomes part of the deployment budget.

Offline compilation scales linearly

State preparation increases linearly with tool count, but compilation is separated from online inference. For RWKV-7 1.5B, one state takes about 0.14 s on a single RTX 3090; 1,000 states would therefore take roughly 140 s in the same setup.
