ENGRAMSTATE · TECHNICAL NOTES

Notes from building
a state-based tool caller.

Short explanations of the design choices behind EngramState: why repeated tool prompts are costly, why the method separates Base and Corrective states, and how recurrent states are stored for mobile deployment.

Technical note 01

Why repeated tool prompts are expensive

Static tool knowledge is useful, but repeatedly prefilling it is not. This note motivates compiling it into reusable recurrent states.

→ Technical note 02

Why EngramState uses Base and Corrective states

Separate the common path from difficult cases so most requests stay lightweight while targeted correction remains available.

→ Technical note 03

Storing recurrent states at 4 bits

State reuse trades prompt compute for persistent storage. Quantization makes that trade practical on mobile hardware.
