Why EngramState uses Base and Corrective states

Most queries need the ordinary tool contract. A smaller fraction need extra knowledge about failure modes. EngramState keeps those two paths separate.

A single tool specification can contain two very different kinds of information. The first is the stable, canonical contract of the API. The second is knowledge accumulated from cases where the model tends to fail.

Base State: the common path

The Base State represents the information that should be available for ordinary calls: tool name, description, arguments, value formats, and canonical examples.

Because this is the path used most often, EngramState keeps it focused. A successful Base attempt ends immediately with a validated function call.

Corrective State: targeted repair

The Corrective State stores harder cases and failure-oriented guidance: confusing values, parameter conventions, known error patterns, and corrective examples.

This information is useful, but forcing every request to carry it would make the common path unnecessarily heavy. EngramState instead loads it only when the Base attempt needs correction.

User query
   ↓
Retrieve candidate tool
   ↓
Load Base State
   ↓
Generate call
   ├── valid → execute
   └── error → load Corrective State → retry
The design goal is asymmetry: make ordinary cases cheap while preserving a deliberate path for difficult ones.

Retries without restarting everything

The same Top-K candidate list is traversed across attempts. EngramState does not need to rebuild a giant prompt for every retry. Each candidate's Base and Corrective states are attempted at most once within the traversal.

That structure also extends to multi-call execution: after one candidate succeeds, the search can continue from the remaining candidates rather than restarting from the beginning.

Why not compile everything into one state?

One large state could mix canonical and corrective information, but that makes every query pay for rare hard cases. Splitting the state gives the runtime a smaller common path and makes the retry behavior easier to reason about and inspect.
