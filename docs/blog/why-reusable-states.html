Technical note 01 · Motivation

Why repeated tool prompts are expensive

Tool descriptions are mostly static. A mobile agent should not have to reread the same instructions every time the user asks for something new.

Function-calling models usually receive a user query together with a collection of tool specifications. Those specifications describe function names, arguments, formats, constraints, and examples. They are important — but they rarely change from one interaction to the next.

The repeated-prefill problem

In a conventional prompt-based pipeline, static tool text is concatenated with every live query. Even a very short request can therefore trigger a long prefill before the model generates its first output token.

User query + Tool 1 spec + Tool 2 spec + ... + Tool N spec
                         ↓
                     Prefill
                         ↓
                    Tool call

For cloud-scale serving this can be absorbed by large accelerators and batching. On a phone, repeated context processing becomes much more visible because latency, memory bandwidth, and energy are constrained.

EngramState asks a different question: if the tool instructions are static, can the model consume them once and reuse what it learned at runtime?

Compile knowledge into model state

Stateful language models expose a recurrent state that summarizes the prefix processed so far. EngramState treats that state as a reusable deployment artifact. A tool specification is consumed offline in a single forward pass, the final recurrent state is retained, and the logits are discarded.

At runtime, the live user query retrieves the relevant stored state. The model can then continue from the restored state rather than reprocessing the entire textual specification.

Offline
Tool specification → Stateful LM → Reusable tool state

Runtime
User query → Retrieve state → Load → Generate tool call

What changes at runtime?

In our representative RWKV-7 1.5B DroidCall setting, the live prompt drops from 985 tokens to 22 tokens. Corresponding TTFT drops from 7.301 s to 0.259 s.

The important shift is not merely prompt compression. Static knowledge moves out of the repeated inference path entirely and becomes reusable model memory.

Why this is useful for on-device agents

Local agents often operate over a stable catalog of device capabilities: alarms, timers, calendars, settings, media controls, and application APIs. Those capabilities are natural candidates for offline compilation because the descriptions change much less frequently than user queries.

EngramState therefore trades repeated prompt compute for selectively loaded persistent state — a trade that is particularly attractive when first-token latency matters.
